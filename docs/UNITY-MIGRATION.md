# Unity Migration — handoff and porting guide

> **Status: decision made, migration not started.** This document exists so the work in this
> repository survives a cold start — a new chat, a different AI, or you coming back in six months.
> Chat context does not persist; this file does. Read this first before touching the Unity project.
>
> **Companions:** `BACKLOG.md` (feature state), `docs/ART-DIRECTION.md` (the visual pivot and why),
> `BLENDERTODO.md` (asset briefs, still valid in Unity), `CHANGELOG.md` (what shipped when).

---

## 1. The decision, and the reasoning behind it

**Target: Unity, shipping to mobile (iOS + Android). Development machine is macOS**, which matters
— macOS + Xcode is the only configuration that can build for iOS at all, so both stores are
reachable from one machine.

**Why the switch was made** (recorded honestly, including the arguments against, so this can be
re-evaluated rather than treated as settled truth):

- **For:** Asset ecosystem. The single biggest practical pain in the web build was assembling a
  coherent look from mismatched free assets — see `docs/ART-DIRECTION.md` for the full diagnosis.
  Unity's asset ecosystem makes a consistent art style far easier to obtain.
- **For:** Mobile-native is the stated target. App-store presence, push notifications, offline
  play and the performance headroom for a 3D world are all materially better native than in a
  mobile browser.
- **For:** Animation/rigging authoring. Unity's Animator handles state machines, blending and
  retargeting as first-class features. In three.js all of that is hand-wired.
- **For (and do not discount this):** motivation. On a multi-year solo project, a stack the
  developer enjoys working in beats a technically-adequate stack they avoid.
- **Against, and still true:** an engine audit (see §6) established that three.js was *not* the
  technical ceiling. The animation problems found were **bugs**, not engine limits — the models
  already shipped 76- and 95-clip libraries that the code simply failed to select from. Unity
  would not have found those bugs, nor supplied those clips.
- **Against, and still true:** browser instant-play is a real distribution advantage that a
  native build gives up. A link that plays in two seconds is the best tool for getting the first
  fifty players.
- **Against, and unresolved:** **the differentiator is still undefined.** See §7. Unity fixes the
  graphics and asset-pipeline frustration. It does not answer "why would someone play this."

### Workflow constraint that shapes the architecture

Development is **mostly phone chat, occasionally at the desktop.** Unity's Editor cannot run on
mobile — there is no iOS/Android Unity Editor, and this is not a limitation with a workaround.

The consequence is a hard architectural rule for the Unity project:

> **Prefer code and data over Editor GUI work.** Every hour of required drag-and-drop Inspector
> wiring is an hour that can only happen at the desk. Scenes assembled by script, prefabs built by
> editor tooling, and content loaded from JSON can all be authored remotely and applied in batches.

This is not a style preference — it is what makes remote/AI-assisted development viable given the
workflow. Concretely: favour `ScriptableObject` assets generated by an editor script over
hand-created ones, build zone content from the existing JSON rather than hand-placing it in a
scene, and keep prefab composition in code where it is reasonable to do so.

## 2. What is in this repository (inventory)

~10,500 lines of game code across 43 modules, 686 automated tests, 86 3D models (41 MB).

### Ports directly — content and design data (the most valuable part)

This is years-equivalent of design and balance work, and **none of it needs redesigning.** It is
data; it needs re-serialising into whatever form the Unity project prefers (JSON via
`JsonUtility`/Newtonsoft, or generated `ScriptableObject` assets).

| Source | Contents |
|---|---|
| `public/cards.js` | **47 cards** across 7 schools, with cost/attack/HP/effects, plus rarity and school tables |
| `public/creatures.js` | creature identities and passive traits |
| `public/archetypes.js` | enemy personalities, thematic decks, multi-phase boss behaviour |
| `public/items.js` | equipment, materials, recipes, home upgrades |
| `public/nodes.js` | gathering node table (mining/woodcutting/fishing) |
| `public/lessons.js` | **21 classes** — briefs, assignments, taught techniques |
| `public/academy.js` | 7 curriculum years and their perks |
| `public/reputation.js` | per-NPC standing tiers and bonuses |
| `public/zonequests.js` | quest chains with prerequisites, objectives, rewards |
| `public/dungeons.js` | dungeon room layouts, enemies, bosses |
| `public/structures.js` | academy building/NPC/prop placement and collision shapes |
| `public/world/zones.json` | **6 zones** — terrain params, spawns, exits, scatter, resource nodes, NPCs |

### Ports directly — assets

- **86 GLB models** (`public/assets/`). Unity imports glTF via the *glTFast* package (recommended)
  or converts to FBX. Rigs and animation clips come across intact.
- Note the rigs differ: `player_wizard.glb` is Mixamo-style (19 joints); the KayKit/Quaternius
  characters use a different 41-joint skeleton. Unity's **Humanoid** rig configuration can
  retarget between them — this is a genuine Unity advantage over the web build, where different
  skeletons meant animation could not be shared (see §6).

### Needs rewriting in C#

| Source | Lines | Notes |
|---|---|---|
| `public/game.js` | 1400 | save/load, migration, economy, gathering, crafting, progression |
| `public/world.js` | 2533 | 3D world rendering, movement, collision, chunk streaming — **largely replaced by Unity built-ins**, not ported line-for-line |
| `public/battle3d.js` | 580 | duel arena presentation |
| `logic.js` | 313 | the online duel referee (stateless, sandboxed) |
| `public/worldconfig.js` | 380 | zone loading, deterministic scatter, chunk bucketing |
| `public/terrain.js` | 199 | heightmap generation and biomes |

Much of `world.js` should **not** be ported: chunk streaming, collision, camera control and
terrain are engine responsibilities in Unity. Port the *rules*, discard the *plumbing*.

### The tests are a porting specification — use them

**644 engine checks** in `tools/test.mjs`, plus online-duel and creature-rule suites. These
document exactly how every rule is supposed to behave. Porting against them turns a rewrite from
a redesign into a translation with a known-good reference. **Recommended: port a system, then
port its tests, and do not consider it done until they pass in C#.** This is the single biggest
de-risking asset available, and most rewrites do not have it.

## 3. Suggested porting order

Ordered so something is playable early and the riskiest unknowns surface first.

1. **Card + duel engine** (`cards.js`, `logic.js`, `archetypes.js`, `creatures.js`) — pure logic,
   no rendering, directly testable against the existing suite. Proves the translation approach
   before any 3D work.
2. **Save/economy core** (`game.js`) — save schema, migration, currency, inventory.
3. **One zone, end to end** — import zone JSON, terrain, one dungeon. The vertical slice, not the
   whole world.
4. **Duel presentation** — Animator state machines for creatures (see §6 for the clip-role work
   already done; the *role* concept ports even though the code does not).
5. **Everything else** — quests, curriculum, reputation, dorm, PvP, cosmetics.

Do **not** port all 43 modules before anything is playable.

## 4. What NOT to rebuild

Three.js required hand-rolling things Unity provides. Delete rather than port:

- Chunk streaming / load-unload hysteresis → Unity's scene streaming and culling
- Manual GPU disposal → Unity's asset lifecycle (the memory-leak class of bug simply does not
  exist in the same form)
- Procedural bone-posed walk cycles → Animator + retargeting
- Hand-built collision resolution → Unity physics/`CharacterController`
- Camera collision → Cinemachine
- Canvas-generated textures → real texture assets

## 5. Known gaps, carried forward

These are unfixed and follow the project into Unity:

- **`professor.glb` has zero skeleton and zero animation clips** — a static statue. It can never
  animate in *any* engine. Needs replacing, not porting.
- **The player rig is thin** — `player_wizard.glb` ships only `Idle` and `Walk`. It is also a
  single mesh with one material, so hats/robes/boots cannot be shown as separate geometry. See
  `BLENDERTODO.md` Tier 5. Unity's Humanoid retargeting makes the *animation* half far easier;
  the *segmented-mesh* half still needs an authored asset.
- **No backend.** Guilds, leaderboards, true multiplayer, cloud save and player presence are all
  blocked on server infrastructure that does not exist. This is unchanged by the engine choice.
- **The differentiator is undefined.** See §7.

## 6. Engineering findings worth carrying over

Real bugs found and fixed in the web build. The **fixes** do not port, but the **lessons** do —
several are mistakes just as easy to make in Unity.

- **Animation clips must be selected by role, never by index.** `battle3d.js` played
  `gltf.animations[0]` as a creature's idle. glTF stores clips in authoring order, and in the
  Quaternius packs clip 0 is `Death` — so **19 creatures looped their own death animation** in
  every duel. `world.js` had the same bug differently shaped: it took the first non-walk clip, so
  `npc_mage` (76 clips) and `enemy_skeleton` (95 clips) idled on `1H_Melee_Attack_Chop`.
  *In Unity:* the Animator makes this harder to get wrong, but name-based clip assignment across
  mismatched packs is still manual — the naming conventions in these assets genuinely disagree
  (`Idle`, `MonsterArmature|Idle`, `Armature|Idle|baselayer`, `1H_Melee_Attack_Chop`, and
  `HitRecieve`, misspelled in the source pack).
- **Rich rigs were shipping unused.** `npc_mage.glb` and `enemy_skeleton.glb` ship real
  `Walking_A` clips that the web build never played. Audit what each imported model actually
  contains before authoring anything new.
- **Asset coherence is a texture problem, not a polycount problem.** See `docs/ART-DIRECTION.md`.
  KayKit-style assets share one material and differentiate parts via a small colour-swatch atlas;
  a blanket re-texture destroys that. Understand an asset's material scheme before batch-editing.
- **Verify against a running build, not against reasoning.** The genuinely severe findings this
  session — a 633 MB heap leak over 20 zone changes, an async chunk-load race, the death-loop —
  were all found by *measuring*, not by reading code. Keep that discipline; Unity has a Profiler.

## 7. The open question Unity does not answer

**What makes someone choose this game?** This is unresolved, and it is the highest-leverage
question in the project.

What is known: the intended pull is **"the world — exploring, discovering, belonging somewhere"**
(Wizard101/RuneScape-flavoured), with a session shape that is **snackable but deep**. Ambition is
a serious long-term project.

What is honest: as of the migration, the game is a broad, well-tested *systems sandbox* — 47
cards, 6 zones, 4 dungeons, quests, reputation, curriculum, economy, PvP, cosmetics — without a
sharp identity. Breadth is not the problem; it is genuinely impressive. The missing piece is a
reason to play *this one*.

**Recommendation carried into Unity:** before rebuilding all 43 systems, build the smallest slice
that expresses "a world worth being in" and put it in front of a handful of real people. Their
reaction is worth more than any amount of further systems work — or engine deliberation.

## 8. Practical setup notes for the Unity project

- **Unity LTS**, 3D URP template (mobile-appropriate; not HDRP).
- **glTFast** package for importing the existing 86 GLBs.
- Configure imported humanoid characters as **Humanoid** rigs to enable animation retargeting
  between the mismatched skeletons.
- Keep this repository. Either add the Unity project alongside the web build in a subdirectory, or
  create a new repo and keep this one as the reference for data, tests and design rationale.
  **Do not delete it** — the tests are the porting spec and the data is the content.
- Given the phone-first workflow (§1), invest early in an editor script that ingests
  `public/world/zones.json` and the data modules directly, so content changes stay data edits
  rather than Editor sessions.
